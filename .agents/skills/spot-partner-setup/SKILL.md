# Set up a Spot partner app

Use this existing checkout and preserve the trading UI, wallet sequence, reviewed quote protections, and history. Read the repository `README.md`, `.env.example`, and the adjacent [spot-theme skill](../spot-theme/SKILL.md). Follow current source if these instructions become stale. Do not scaffold a replacement app.

The partner app must retain the reference app's layout, spacing, typography, responsive behavior, and components regardless of app or partner ID. Change only branding (name, logo, colors, and related metadata) unless the user explicitly requests another UI change. Developer-tool removal below is a separate cleanup and must not alter the production trading interface.

## Turn a brief into a working fork

Reuse the user's name, logo, colors, mode, partner identifier, URLs, network choices, and other supplied details. Apply the theme skill without asking the user to invoke it or provide individual CSS tokens. If choices are missing, make reasonable reversible defaults or ask only when the choice is necessary; offer text-only branding when no logo is available. Do not fabricate logos, credentials, partner activation, or a partner identifier. Distinguish `APP_ID` (a stable app/RPC identifier) from `NEXT_PARTNER` (the public Spot partner identifier sent to the service). The latter defaults to `external` and is embedded in the browser build; use a different value only if supplied or confirmed. SDK initialization does not prove partner activation on a chain.

Preserve existing local changes and environment values. Put partner-specific values in ignored `.env.local`, keeping unrelated entries; do not print secrets or copy credentials from unrelated projects. Check `.env.example` and the Next.js environment precedence in the installed Next documentation. Set the name, ID, metadata, image paths, default mode, and theme values requested by the brief. The optional `NEXT_PUBLIC_PROJECT_ID` belongs to the partner's WalletConnect project; without it, browser-injected wallets and Safe apps remain available, but WalletConnect pairing is disabled. `RPC_URLS` maps chain IDs to server-side RPC URLs; `RPC_URL` is an alternative chain-aware gateway. The app requires one RPC configuration. If it is missing, continue independent configuration and report what prevents a real preview; never invent credentials. `NEXT_PUBLIC_APP_URL` is wallet metadata, not a replacement for the provider's origin allowlist.

The minimal `.env.example` contains empty placeholders for the WalletConnect ID, RPC gateway, and partner. Preserve existing local values and add optional branding, theme, or other configuration directly to `.env.local` as needed; those settings do not need to appear in `.env.example`. A supplied RPC URL does not establish that the partner is enabled for live trading.

Values prefixed `NEXT_PUBLIC_` are public and inlined at build time. Branding is also applied during build/prerender; restart the dev server and rebuild after changes. Keep secrets out of public values and source control. Assets go in `public/` and URLs use root-relative paths or suitable HTTPS URLs.

## Remove developer tools for the partner fork

Unless the user requests keeping them, remove the reference-only playground and debug surfaces from the partner fork before preview or release. If the user requests keeping `/dev`, debug, or API overrides in their deployment, retain those features and verify them rather than applying this cleanup. Keep cleanup scoped to the partner checkout; the upstream reference retains its developer UI. Preserve production swap, advanced-order, order-history, wallet, and settlement behavior.

- Remove `/dev` and its child routes, the legacy developer inspector route, developer navigation, Demo controls, inspectors, walkthroughs, mock orders, SDK download UI, and their unused feature modules, assets, aliases, and imports. Audit both `@developer-tools` and `@developer-inspector` consumers before deleting them; replace developer-specific branches with the normal production behavior rather than leaving broken imports.
- Remove `debug=true` behavior and partner testing controls, including the debug partner selector and debug-only history columns. Ignore debug and partner query overrides rather than letting URL parameters change the configured partner. Remove test-backend selection and related query propagation where it exists solely for debugging; retain the production backend and the configured `NEXT_PARTNER`. Keep the network availability checks for that actual partner. Remove dead developer redirects, flags, and links from navigation, configuration, and documentation.
- Do not remove the partner's trading forms, normal order details/history, real quote refreshes, reviewed minimums, wallet guards, or cancellation and settlement logic. Consult the bundled Spot SDK integration skills before touching these paths. Do not replace missing live services with mocks or test-mode shortcuts.

Additional cleanup candidates in this checkout:

- Once all consumers are removed, delete `features/developer-tools/`, `features/eip712-inspector/`, `features/partner-selector/`, developer route helpers, the `@developer-tools` and `@developer-inspector` aliases, and their developer-only CSS selectors. Remove the inspector-only `prism-react-renderer` and `react-json-view-lite` dependencies and the latter's import in `app/globals.css` if no consumers remain, using Yarn so the lockfile stays consistent. Keep `react-virtuoso`: token selection and real order history use it.
- Remove sample order creation and `mockorders` branches from history and cancellation only after eliminating all sample-order entry points. Retain the actual wallet, account, chain, order status, and duplicate-cancellation checks. Delete the sample module when it has no consumers.
- Simplify debug-only route and query plumbing in `components/app-link.tsx`, `lib/developer-routes.ts`, `lib/hooks/use-developer-mode.ts`, `lib/hooks/use-spot-partner.ts`, `lib/spot/api.ts`, and debug-dependent history columns. Audit `lib/spot/order-link.ts` and `lib/swap/activity.ts` before removing test API URLs: persisted pending swaps can reference older backends. Preserve recovery and existing order links or explicitly migrate/resolve legacy records; never silently drop an uncertain or pending submission. Keep configured-partner and configured-RPC network filtering in `use-spot-partner-chains` and its shared fetch/parser even if the debug selector is removed.
- Remove the debug-only redirects and their docs URL setting in `next.config.ts` and any environment configuration if no longer used. Remove unused playground docs and standalone download examples only when the fork no longer needs them; update links and typecheck includes. Keep deployment configuration specific to the partner’s own host. Do not delete general runtime configuration or route handlers needed by production.
- Audit leftover reference branding and assets against actual imports. Orbs attribution in the Spot route, protocol information, SDK service endpoints, and required legal links are not automatically developer UI; retain them unless the user explicitly requests a change and the replacement remains accurate. Likewise, a custom wallet picker or theme assets may still be used; remove them only after confirming they have no production consumers.

Audit the resulting source for stale `/dev`, `debug`, developer aliases, demo and inspector references, then run the checks below. Confirm `/dev` and its subroutes and the legacy inspector no longer serve developer tools; verify `?debug=true` and old debug query parameters do not expose controls or alter the production partner/backend. Keep a user's explicit later request to retain a specific tool as an exception.

## Preview and verify

Install dependencies from the lockfile if needed using the versions documented in `README.md`. Start `yarn dev`, use its actual URL, and inspect the real app in desktop and mobile layouts. Check both themes, branding, metadata, and the wallet dialog when configuration allows. Exercise the production swap and advanced-order forms without wallet signing or live submission; check quote loading, errors, and unchanged review protections. Confirm the removed developer routes and debug overrides remain unavailable. Run `yarn typecheck`, `yarn lint`, and `yarn build`; report missing credentials, network failures, and untested states accurately.

Compare the reference app and partner app side by side at the same desktop and mobile viewport sizes and the same light and dark themes. Compare corresponding production routes and UI states, including navigation, swap and advanced-order forms, history, menus, and dialogs when available. Check layout, spacing, typography, components, and responsive behavior; fix unintended differences while allowing the requested branding. Use an accessible reference deployment or an unmodified reference checkout; if either app cannot be compared, report the limitation instead of claiming parity.

If changing SDK integration or partner behavior, follow the matching versioned SDK skill under `node_modules/@orbs-network/spot-ui/dist/integration-skills/` and its relevant references. Preserve the actual partner/chain identity; never switch partner or invent contracts to make a preview pass. A working UI or build does not establish live trading activation. Do not sign or submit real transactions without authorization.

## Hosting and handoff

Only deploy when the user requests it. This Next.js app has server routes and needs a host that supports them; a static-only upload is insufficient. Use a deployment workflow configured for the partner’s own project. For an authorized deployment, inspect the chosen host and project ownership, configure both build and server runtime values appropriately, set a shared host-level rate limit for all three RPC-backed API routes, and use the host's supported Next.js workflow. Report the URL, actual checks, wallet origin setup, and separately whether partner/chain activation was verified. Never infer activation from a published page.
